# ComHub 桌面端控制中心设计

## 1. 背景

ComHub 已经具备桌面客户端、Electron 自动更新器、公开桌面配置、S3 兼容发布动作和 GitHub Actions 发布工作流，但这些能力尚未形成完整的后台控制面：

- `/settings/admin/desktop-update` 当前仍是实验状态的长表单，只能编辑部分设置。
- `.github/workflows/comhub-desktop-release.yml` 可以构建 Windows 安装包、发布到对象存储，并回写最新版本，但后台不能查看或触发发布任务。
- `apps/server/src/services/desktopRelease` 能解析更新清单和安装包，却没有接入后台状态查询。
- `devices` 与 Device Gateway 能描述用户设备及在线通道，但没有桌面安装实例、客户端版本、架构、升级状态和管理状态。
- 桌面端能读取公开更新配置，但不支持最低版本、强制升级、灰度比例、维护公告或受管实例停用。

本设计将这些能力收敛为后台唯一的“桌面端控制中心”，并保留 GitHub Actions、对象存储、Device Gateway 和现有应用设置各自的职责边界。

## 2. 目标

1. 在一个后台入口统一查看桌面发行状态、安装包、客户端资产和更新策略。
2. 从后台安全触发正式发布、预发布和回滚任务，并跟踪全过程。
3. 建立桌面安装实例清单，展示版本、渠道、平台、架构、用户、在线状态和最后上报时间。
4. 支持受管实例停用、最低版本、强制升级、灰度发布及维护公告。
5. 统一桌面登录页、下载入口、业务连接和更新服务设置。
6. 所有危险操作具备权限校验、原因记录、状态反馈和审计日志。
7. 不在数据库或浏览器中保存发布密钥、GitHub Token、OSS Secret 等部署凭据。

## 3. 非目标

- 不提供任意远程 Shell、文件访问、进程控制或软件卸载能力。
- 不把宝塔、GitHub Actions 或对象存储的完整管理界面复制进 ComHub。
- 不把通用 CLI、浏览器会话和移动设备错误地统计为桌面安装实例。
- 不承诺通过“停用”删除用户电脑上的程序；停用只撤销该受管实例的控制面资格并限制客户端功能。
- 不用后台数据库配置替代构建时的 `OFFICIAL_CLOUD_SERVER`，正式业务服务地址仍由发布流水线注入。

## 4. 方案选择

### 4.1 方案 A：只重做设置页

把现有长表单改成分组页面，继续手工维护版本和下载链接。

优点是交付快、改动小；缺点是不能回答发布是否成功、哪些安装包可用、用户正在运行什么版本，也不能完成客户端治理。因此不采用。

### 4.2 方案 B：发行控制台与安装实例管理，共用现有基础设施

保留 GitHub Actions 作为构建发布执行器、对象存储作为制品源、应用设置作为公开策略源；新增后台发行编排、发布记录和桌面安装实例模型。

该方案能形成完整控制面，同时不把构建和远程设备能力塞进 Web 进程。此方案为推荐方案并作为实施基线。

### 4.3 方案 C：完整 MDM/远程控制平台

建设常驻管理 Agent、命令队列、设备证书和系统级策略。

该方案可以远程卸载和执行系统命令，但安全、隐私和运维成本远超当前需求，也会扩大桌面客户端攻击面。因此不采用。

## 5. 信息架构与页面

现有路由 `/settings/admin/desktop-update` 保持不变，菜单名称从“桌面客户端”调整为“桌面端控制中心”，状态从 `experimental` 变为 `active`。页面由紧凑页头、状态带和六个页签构成，不使用嵌套卡片。

### 5.1 总览

- 状态带：Stable 版本、Canary 版本、在线客户端、待升级客户端、最近发布结果。
- 平台矩阵：Windows、macOS Intel、macOS Apple Silicon、Linux 的清单状态、安装包名称、大小和发布时间。
- 版本分布：当前活跃安装实例的前五个版本及占比。
- 风险提示：更新服务器不可达、清单损坏、安装包缺失、版本配置与清单不一致、发布凭据未配置。
- 最近活动：发布、回滚、停用和策略变更的审计摘要。

所有区域提供 loading、empty、error 和 populated 四种状态。错误状态显示可执行的重试动作；未配置状态显示前往对应设置页签的动作。

### 5.2 版本发布

- 发布列表：版本、渠道、提交、状态、触发人、开始时间、完成时间和工作流链接。
- 唯一主操作为“创建发布”。表单包含版本、渠道、发布说明、目标平台和是否发布制品。
- 创建发布采用“确认 -> 执行中 -> 完成/失败”的同一模态流程，执行中禁止重复提交。
- 历史版本支持查看制品与“设为当前版本”。该操作触发受保护的清单切换工作流，不直接从 Web 进程写对象存储。
- 同一渠道同时只允许一个构建或回滚任务。

### 5.3 安装分发

- 展示每个平台和架构的当前安装包、校验值、大小、发布时间和下载状态。
- 可配置公开下载按钮文案、默认下载地址和备用下载地址。
- 自动解析清单中的安装包优先于手工覆盖地址；手工覆盖必须明确标注来源。
- 不可用平台显示缺失原因。macOS 签名凭据未配置时，不显示虚假的可下载状态。

### 5.4 客户端

- 支持按用户、设备名、平台、版本、渠道、在线状态和管理状态筛选。
- 表格采用服务端游标分页；默认每页 20 条，面向 1 到 10,000 条记录设计。
- 详情抽屉展示安装实例、关联用户、设备信息、版本、策略状态、最近上报和管理操作历史。
- 单条与批量操作保持一致：停用、恢复、要求检查更新。
- 停用必须填写原因。停用后实例不能继续上报或使用受管桌面能力，但用户仍可通过 Web 登录，也可以重新安装并重新注册。

### 5.5 更新策略

- 默认渠道、自动检查、检查间隔。
- 自动下载、退出时自动安装。
- 最低支持版本、强制升级目标版本、强制升级截止时间和提示文案。
- 灰度比例为 0 到 100，使用安装实例 ID 做稳定散列，同一实例不会在灰度组之间跳动。
- 最低支持版本与强制升级不受灰度比例影响。
- 维护公告支持启用、内容和生效区间。
- 保存前显示影响预览：受影响安装实例数量、版本分布和预计强制升级数量。

### 5.6 品牌设置

- 登录窗口标题、Logo、主标题、副标题、云端登录按钮和版权文案。
- 公开下载入口文案。
- 业务服务地址只读展示，并提示其构建时来源。
- 更新服务器可编辑；OSS Bucket、Endpoint 和凭据状态只读展示。
- 普通设置批量保存；未保存草稿存入当前管理员浏览器的本地存储，保存成功后清除。

## 6. 系统架构

### 6.1 后台页面

`src/features/Admin/DesktopControlCenter/` 承载业务 UI，路由文件继续保持薄层。建议拆分为：

- `OverviewPage.tsx`
- `ReleasesPage.tsx`
- `DistributionPage.tsx`
- `ClientsPage.tsx`
- `PolicyPage.tsx`
- `BrandPage.tsx`
- `components/`
- `hooks/`
- `types.ts`

原 `AdminDesktopUpdatePage.tsx` 只保留兼容导出或删除后由新入口替换，避免继续扩展单个大文件。

### 6.2 后台 API

在 `packages/business-server/src/lambda-routers/admin/desktop.ts` 新增 `admin.desktop` 路由，按能力拆分：

- `getOverview`
- `listReleases`
- `getRelease`
- `dispatchRelease`
- `dispatchRollback`
- `listInstallations`
- `getInstallation`
- `disableInstallations`
- `restoreInstallations`
- `getPolicyImpact`

读取操作使用 `systemRead`，写入与发布操作使用 `systemWrite`。危险操作继续使用项目现有的 Admin Command 与审计模式。

客户端上报使用独立的受认证路由 `desktopClient`：

- `registerInstallation`
- `reportInstallation`
- `getManagedPolicy`
- `acknowledgePolicy`

公开下载与登录品牌仍通过现有 `getPublicDesktopUpdate` 提供；实例级状态不进入公开接口。

### 6.3 服务层

扩展 `apps/server/src/services/desktopRelease/`：

- 同时解析 Stable 和 Canary。
- 返回平台级清单、制品、大小、校验值和健康诊断。
- 对网络请求设置超时、响应大小限制和允许的协议。
- GitHub API 调用集中在服务端，Token 不进入 tRPC 输出。

新增 `apps/server/src/services/desktopRelease/github.ts` 负责工作流触发和运行状态读取；新增 `policy.ts` 负责版本比较、灰度分桶和策略解析。

### 6.4 GitHub Actions

保留 `.github/workflows/comhub-desktop-release.yml` 为构建发布执行器，并增加：

- 可选 `release_id`，用于关联后台发布记录。
- 发布开始、成功和失败回调。
- 平台制品摘要回调。
- 工作流运行 URL 和 commit SHA 回写。

新增受保护的清单切换工作流用于回滚。它只将已归档版本的清单复制到渠道根目录，不重新构建二进制。生产回滚必须经过 GitHub Environment 保护规则。

## 7. 数据模型

### 7.1 `desktop_releases`

字段：

- `id`: UUID 主键。
- `version`: 规范化语义化版本。
- `channel`: `stable | canary`。
- `status`: `queued | building | publishing | succeeded | failed | rolling_back | rolled_back`。
- `commitSha`, `workflowRunId`, `workflowRunUrl`。
- `releaseNotes`, `updateServerUrl`。
- `artifacts`: 平台制品摘要 JSON，不保存凭据。
- `createdBy`, `startedAt`, `completedAt`, `publishedAt`。
- 标准 `createdAt`, `updatedAt`。

`channel + version` 唯一。状态转换由服务端校验，禁止从终态回到构建态。

### 7.2 `desktop_installations`

字段：

- `id`: UUID 主键，同时作为稳定灰度分桶键。
- `userId`, `deviceId`。
- `platform`, `arch`, `osVersion`。
- `appVersion`, `buildChannel`。
- `status`: `active | disabled`。
- `lastPolicyVersion`, `lastUpdateCheckAt`。
- `firstSeenAt`, `lastSeenAt`。
- `disabledAt`, `disabledBy`, `disabledReason`。
- 标准 `createdAt`, `updatedAt`。

客户端本地生成并持久化安装实例 ID。重新安装生成新实例，避免把历史停用状态错误继承给新安装。

在线状态不单独持久化：`lastSeenAt` 在五分钟内视为在线，避免对 Device Gateway 做按用户扇出查询。Device Gateway 在线通道只在详情页作为补充信息。

## 8. 设置契约

现有 `desktop.*` 设置继续保留，并增加：

- `desktop.management.enabled`
- `desktop.update.autoDownload`
- `desktop.update.autoInstallOnQuit`
- `desktop.update.minimumVersion`
- `desktop.update.forceVersion`
- `desktop.update.forceDeadline`
- `desktop.update.forceMessage`
- `desktop.update.rolloutPercentage`
- `desktop.maintenance.enabled`
- `desktop.maintenance.message`
- `desktop.maintenance.startsAt`
- `desktop.maintenance.endsAt`

这些键必须进入统一设置注册表、值定义、后台读模型、公开/受管读模型和缓存失效映射，不在前后端重复维护另一份无校验键表。

## 9. 核心流程

### 9.1 创建发布

1. 管理员提交版本、渠道、平台和说明。
2. 服务端校验语义化版本、渠道并发和 GitHub 配置。
3. 数据库创建 `queued` 发布记录并写审计日志。
4. 服务端使用 `DESKTOP_RELEASE_GITHUB_TOKEN` 触发 GitHub Actions。
5. 工作流回调更新构建、发布和制品状态。
6. 成功后更新公开桌面设置并失效缓存。
7. 后台轮询或 SWR 刷新状态；失败保留原输入并给出工作流链接。

若 GitHub 触发失败，发布记录进入 `failed`，不会只留下永久 `queued` 记录。

### 9.2 客户端注册和上报

1. 已登录桌面客户端取得主进程提供的版本、平台、架构和安装实例 ID。
2. Renderer 通过用户会话调用 `registerInstallation`。
3. 启动、恢复前台、检查更新和固定心跳时调用 `reportInstallation`。
4. 服务端只接受当前用户拥有的安装实例，拒绝跨用户修改。
5. 上报间隔设置下限，防止异常客户端写放大。

### 9.3 强制升级

1. 客户端获取实例级受管策略。
2. 服务端使用语义化版本比较和稳定灰度分桶计算结果。
3. 截止时间前显示非阻断提醒；截止时间后进入阻断更新页。
4. 更新页只提供下载更新、重试策略和退出，不遮挡安装进度。
5. 客户端缓存最近一次有效策略；网络失败时提供最长 24 小时宽限，避免配置故障永久锁死客户端。

### 9.4 停用与恢复

1. 管理员选择实例并填写原因。
2. 服务端确认权限、实例数量和目标状态。
3. 更新实例状态并写审计日志。
4. 客户端下一次策略获取或心跳收到停用状态，停止 Device Gateway 和受管后台功能并显示停用页。
5. 恢复后重新获取策略即可继续使用。

停用不是账户封禁。若需要禁止用户全部入口，应使用现有用户封禁功能。

### 9.5 回滚

1. 管理员选择同渠道已成功发布的历史版本。
2. 后台展示当前版本、目标版本和受影响实例数。
3. 触发受保护的 GitHub 清单切换工作流。
4. 工作流验证归档清单和所有引用制品后，原子替换渠道根清单。
5. 回调更新当前版本和发布记录，失败时保持原清单不变。

## 10. 安全与隐私

- GitHub Token 使用最小权限 fine-grained token，只允许 Actions 读写目标仓库。
- `DESKTOP_RELEASE_TOKEN` 继续用于 CI 回调；使用恒定时间比较并支持轮换。
- OSS、签名、证书和 GitHub 凭据只存在 GitHub Secrets 或服务器环境变量。
- 发布和回滚输入禁止任意 URL、分支和工作流文件名，目标仓库及工作流由服务端配置固定。
- 更新服务器仅允许 HTTPS；开发和测试环境可以显式允许本地 HTTP。
- 清单解析限制响应大小和超时，禁止重定向到非 HTTP(S) 协议。
- 客户端只上报管理所需元数据，不采集文件路径、聊天内容、硬件序列号或 IP 历史。
- 批量停用、回滚和强制升级必须记录原因并执行影响预览。
- 所有列表查询按权限过滤并服务端分页，禁止把完整用户设备表发送到浏览器后筛选。

## 11. 错误处理

- GitHub 未配置：发布按钮禁用，显示缺少的环境变量名称，不显示其值。
- 更新服务器不可达：保留最后一次成功快照并标记为过期，允许手动重试。
- 某平台清单缺失：只标记该平台不可用，不让其他平台总览失败。
- CI 回调重复：按发布 ID 和状态幂等处理。
- CI 回调失联：后台通过 GitHub 运行状态进行对账并修正长期未完成记录。
- 客户端版本不合法：拒绝上报并记录限速诊断，不污染版本统计。
- 批量操作部分失败：返回逐项结果，不把成功项回滚成未知状态。
- 设置保存失败：保留表单和本地草稿，允许原地重试。

## 12. 可观测性

- 记录发布触发、GitHub 请求、回调、清单探测和策略计算的结构化日志。
- 指标包含发布成功率、发布时间、清单探测失败率、活跃安装实例、版本覆盖率和强制升级完成率。
- 不在日志中记录 Token、Secret、完整授权头或安装实例凭据。
- 总览展示产品级诊断，详细技术日志仍留在 GitHub Actions 和服务器日志系统。

## 13. 测试策略

### 单元测试

- Stable/Canary 与各平台清单解析。
- URL、响应大小、超时和错误隔离。
- 语义化版本比较、灰度分桶、强制升级和宽限期。
- 发布状态机和回调幂等。
- 设置注册表、读模型和缓存失效。

### 服务与权限测试

- `systemRead` 与 `systemWrite` 权限边界。
- GitHub workflow dispatch 请求和失败映射。
- 安装实例注册、跨用户拒绝、分页和批量停用。
- 审计记录包含操作者、目标、原因和结果。

### UI 测试

- 六个页签的 loading、empty、error 和 populated 状态。
- 发布和停用的确认、执行中、完成/失败状态机。
- 草稿恢复、影响预览和设置保存。
- 1、20、100 和 10,000 条安装实例下的分页与筛选契约。

### 桌面端测试

- 安装实例 ID 持久化。
- 元数据上报节流。
- 强制升级截止时间、离线宽限和恢复。
- 停用后受管能力关闭、恢复后重新启用。
- 原有手动检查、下载、稍后安装和渠道切换行为不回归。

### 发布契约测试

- 工作流输入、回调负载和后台 schema 保持一致。
- 正式构建包含 `OFFICIAL_CLOUD_SERVER` 且不包含上游云地址。
- 回滚只切换经过验证的归档清单。

## 14. 分阶段实施

### 阶段 1：控制中心基础与发行诊断

- 重构后台页面和菜单。
- 扩展清单解析服务，接入总览、平台矩阵和安装分发。
- 整理现有设置为更新策略与品牌页签。
- 建立完整 loading、empty、error 状态。

验收：管理员能从单一入口确认各渠道版本、平台制品、更新服务健康和配置来源。

### 阶段 2：发布编排与历史

- 新增发布表、后台发布 API 和 GitHub 服务。
- 接入工作流触发、状态回调、运行链接和历史记录。
- 新增受保护回滚工作流。

验收：管理员能创建发布、查看全过程，并将渠道安全回滚到已验证历史版本。

### 阶段 3：安装实例资产

- 新增安装实例表和客户端注册/上报。
- 建设客户端列表、详情、版本分布和在线统计。
- 支持筛选、分页、停用和恢复。

验收：后台能准确区分桌面安装实例与其他设备通道，并完成完整管理生命周期。

### 阶段 4：受管更新策略

- 扩展公开和实例级策略契约。
- 桌面端接入灰度、最低版本、强制升级、维护公告和停用状态。
- 提供影响预览、离线宽限和应急恢复路径。

验收：策略命中可预测、可审计、可撤回，网络或配置故障不会永久锁死客户端。

### 阶段 5：审查与上线

- 完成权限、安全、性能、无障碍和响应式审查。
- 执行针对性测试、类型检查和桌面构建验证。
- 先启用观测和上报，再逐步开启管理与强制策略。

验收：默认关闭危险策略，生产启用可回滚，并有明确的监控与故障处理路径。

## 15. 上线与兼容

- 数据库迁移先于应用版本部署，新增字段和表不改变现有设备查询。
- 新客户端上报为渐进增强，旧客户端继续使用现有公开更新配置。
- `desktop.management.enabled` 默认关闭；安装实例上报稳定后再开启管理操作。
- 新增策略字段均有与当前行为一致的默认值。
- 现有 CI 回写接口继续兼容无 `release_id` 的旧工作流请求。
- 页面切换后保留原路由和权限，避免书签与后台导航失效。

## 16. 完成定义

- 后台入口、发布、安装分发、客户端清单、更新策略和品牌设置全部可用。
- 关键实体具备完整生命周期，不存在只能查看不能处理的孤立记录。
- 所有危险操作拥有权限、确认、原因、执行状态和审计。
- 发布凭据不会进入数据库、客户端包、浏览器响应或日志。
- 旧客户端保持可更新，新客户端能注册、上报并执行受管策略。
- 目标测试、类型检查、工作流契约和至少一个生产式桌面构建通过。
- 生产启用步骤和回滚步骤均完成验证。
